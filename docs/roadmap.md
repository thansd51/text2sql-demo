# 유지보수·확장 계획

이 PoC는 **SQL 생성까지**가 범위입니다 (DB 접속과 실행, 로그인 연동은 제외). 아래는 그 다음에 무엇을 어떤 순서로 하면 좋은지에 대한 계획이며, 일정은 정하지 않았습니다.

## 1. 유지보수 원칙

### 1.1 메타데이터가 품질을 좌우합니다
- 메타데이터(`profiles/`, `semantic/`, `examples/`, `datasources/`)는 파일로 두고 **Git으로 변경 이력을 관리**합니다. 변경은 리뷰 후 합칩니다.
- 변경할 때마다 `./scripts/test.sh`(샘플 정합성과 시작 검사)와 `scripts/live_check.py`(실제 모델 확인)를 돌립니다.
- 응답의 `metadata_version`(파일 내용 해시)으로 어떤 메타데이터가 만든 SQL인지 추적합니다.

### 1.2 무엇을 바꿀 때 어디를 고치나

| 하고 싶은 일 | 고칠 곳 | 코드 수정 |
|---|---|---|
| 테이블·컬럼 추가, 규칙·동의어 보강 | `profiles/<제품>/tables/*.yml`, `product.yml` | 없음 |
| 새 프로젝트, 프로젝트별 코드·이름 | `datasources/`, `semantic/` | 없음 |
| 모델이 자주 틀리는 질문 보강 | 해당 테이블의 `rules`, `examples/` | 없음 |
| 새 DB 종류(MySQL, HANA 등) | `dialects/`에 어댑터 추가·등록, `DbType`에 값 추가, 검증 사례 모음 추가 | 있음 (한 폴더) |
| 새 LLM 제공자 | `llm/`에 `LLMClient` 구현 추가, `startup.create_llm`에 연결, 설정값 추가 | 있음 (한 폴더) |
| 새 검증 규칙 | `validation/`, 공격 사례 모음에 사례 추가 | 있음 (한 폴더) |
| 메타데이터 저장 위치 변경(파일 → DB) | `semantic/`의 저장소 인터페이스(`SemanticRepository`) 구현 교체 | 있음 (한 폴더) |

폴더 하나가 개념 하나이고, 교체가 필요한 곳(LLM, DB 방언, 저장소)만 인터페이스로 분리했기 때문에 위 변경이 다른 폴더로 번지지 않습니다.

### 1.3 품질을 지키는 장치
- **자동 테스트 966건 + 화면 64건**: 검증 규칙과 방언은 공격 사례 모음으로 회귀를 막습니다.
- **시작 시 검사**: 메타데이터 오류는 서비스가 뜨기 전에, 파일 이름과 위치와 함께 드러납니다.
- **샘플 정합성 테스트**: 샘플의 모든 행이 테이블 정의의 컬럼을 빠짐없이 가지는지 등을 확인합니다.
- **`live_check.py`**: 실제 모델로 대표 질문을 확인하는 수동 점검입니다. 질문을 늘릴수록 평가셋 역할을 합니다.

### 1.4 의존성
- `uv.lock`으로 고정합니다. `sqlglot`은 버전(`30.30.0`)을 고정했습니다. 올릴 때는 검증·방언 테스트(공격 사례 모음)를 반드시 통과시키세요. 파서 동작이 바뀌면 허용 목록 검증이 달라질 수 있습니다.
- Python 3.12, Node 22 기준입니다.

## 2. 확장 계획

### 2.1 바로 다음 (실제 사용 전에)

| 항목 | 이유 |
|---|---|
| **실제 DB 컬럼 문서와 대조** | `design.md`의 "확인 필요" 목록(예: 항목 허용값 행의 `TYPEID`, `OBJ_MAIN.END_DT` 존재, `VF_DT`/`VT_DT` 종료일 포함 여부, `BASIS`와 `BASIS_YN`)은 실제 DB로만 확정할 수 있습니다 |
| **평가 질문 확대와 자동 채점** | 지금은 11개 질문입니다. 프로젝트·방언·질문 유형별로 늘리고 합격 기준을 정해야 모델·메타데이터를 바꿀 때 좋아졌는지 알 수 있습니다 |
| **조건 누락 검사** | 모델이 `TYPEID <> 0` 같은 필수 조건을 빠뜨릴 수 있습니다. "이 테이블을 쓰면 이 조건이 필수"를 `rules`에 기계가 읽는 형태로 적고, 빠지면 오류를 알려 다시 쓰게 합니다 |
| **실서비스 모델 확정 후 측정** | 모델 크기·컨텍스트·속도에 따라 프롬프트 예산과 테이블 선택 설정(`LLM_CONTEXT_TOKENS`, 글자-토큰 어림값)을 실측으로 조정합니다 |
| **테이블 수십 개 규모 시험** | 질문에 맞는 테이블을 고르는 기능(점수 기반)은 가짜 테이블 12개로만 시험했습니다. 실제 규모에서 필요한 테이블을 놓치는 빈도를 재야 합니다 |
| **접속 키 요청 제한** | 틀린 키를 계속 넣어도 막지 않습니다 (초당 약 130회 측정). 일정 횟수 실패하면 잠시 차단합니다 |

### 2.2 중기

| 항목 | 설명 |
|---|---|
| **메타데이터 DB 저장과 등록 화면** | 지금은 파일을 고치고 서버를 다시 시작합니다. 저장소 인터페이스를 DB 구현으로 교체하고, 화면에서 프로젝트·코드 이름을 등록·수정합니다 (서버는 파일을 쓰지 않는 원칙 유지) |
| **Importer** | DB 카탈로그나 컬럼 문서에서 `profiles/` 초안을 자동으로 만듭니다. 수십 개 테이블을 손으로 쓰는 부담을 줄입니다 |
| **질문 이력과 피드백** | 좋음·나쁨 표시와 질문 이력을 저장하고, 나쁜 사례를 평가 질문으로 옮깁니다 |
| **프롬프트 캐싱** | 프로젝트마다 앞부분이 같으므로 Claude·OpenAI의 캐싱으로 비용과 시간을 줄입니다. 로컬 모델은 이미 앞부분을 재사용합니다 (같은 프로젝트의 연속 질문이 2~5초) |
| **동시 처리** | 로컬 모델 서버는 한 번에 한 요청(`--parallel 1`)입니다. 사용자가 늘면 동시 처리 수, 대기열, 서버 수를 정합니다 |
| **운영 관측** | 요청 번호·검증 실패 사유를 모아 집계합니다 (질문 내용은 로그에 남기지 않는 현재 원칙 유지) |

### 2.3 장기

| 항목 | 설명 |
|---|---|
| **MySQL, HANA 방언** | `dialects/`에 어댑터를 추가합니다 (1.2 참고) |
| **질문과 비슷한 예시 검색(RAG)** | 예시가 많아지면 모두 넣을 수 없습니다. 질문과 비슷한 예시만 골라 넣습니다 |
| **`CREATE VIEW` 생성문 변환** | 지금은 모든 CREATE를 거부합니다. 뷰 생성문 복사 기능은 별도 범위로 합니다 |
| **고객사 시스템과의 실행 연동** | 이 서버는 SQL 생성까지만 합니다. 실행은 고객사 쪽에서, 읽기 전용 계정과 시간 제한을 두고 하도록 권고합니다 |

## 3. 위험과 열린 질문

| 위험 | 대응 |
|---|---|
| 작은 로컬 모델의 SQL 품질 | 규칙·예시·`이름: 조건` 같은 메타데이터 보강으로 대응. 더 큰 모델이 필요한지는 평가 질문 확대 후 판단 |
| 메타데이터 규모 증가 (수십 개 테이블) | 토큰 예산과 테이블 선택으로 대응. 실규모 측정 필요 (2.1) |
| 고객사 메타데이터 반출 | 확인 전에는 샘플·익명화 값만 저장소에 둡니다. 외부 API(OpenAI, Claude)를 쓰면 스키마와 질문이 외부로 전송됩니다 |
| 공개 노출 | 접속 키 필수, 키 길이·요청 제한(2.1). 내 PC를 터널로 공개하는 방식은 시연용으로만 |
| 샘플 가정이 실제와 다름 | 더미 값과 가정은 `README`와 `design.md`에 표시했습니다. 실제 DB 문서로 바로잡아야 합니다 |

## 4. 하지 않기로 한 것 (범위 밖)

- DB 접속과 SQL 실행, SELECT 이외의 SQL 생성·허용
- 서버가 파일을 쓰는 방식의 메타데이터 수정 (배포 환경의 파일시스템이 초기화되므로, 필요하면 DB로)
